# 情境未標註記憶基準：規格草案

狀態：**草案 v0.3（2026-11-12）**。v0.1 的七項決定記在 §12，§13 的四項已在 2026-11-12 確認（見 §13 各點）。對應暫定題目《情境未標註下智能體的情境變動偵測與選擇性記憶利用》。

本文件只定規格，不含程式。結果一律標示為自建協定（`derived_protocol`），不和任何官方 benchmark 的分數並列。

## 1. 要量什麼

一個代理用**同一個記憶庫**，在連續、沒有身分與場景標註的文字互動中，面對不同的人與場景。基準要分開量四件事：

| 編號 | 能力 | 問的問題 |
|---|---|---|
| C1 | 情境變動偵測 | 現在這段互動，和剛才是同一個情境嗎？ |
| C2 | 長期歸屬 | 換了之後，是回到哪個舊情境，還是新的？（跨天、跨週） |
| C3 | 選擇性利用 | 回答時，有沒有用到該用的記憶、避開不該用的記憶？ |
| C4 | 不確定時的行為 | 情境無法判斷時，會不會先確認，而不是猜一個？ |

C1、C2 可以只看記憶系統的內部狀態，確定性計分；C3、C4 要看最後的回答。

## 2. 名詞定義

| 名詞 | 定義 |
|---|---|
| 人（person） | 和代理互動的對象。每人有固定的背景、偏好和說話方式 |
| 場景（scene） | 互動發生的用途或環境，例如工作專案、家庭事務、某個興趣社群。場景有自己的慣例 |
| 情境（context） | 人 × 場景的組合 `c = (p, s)`。同一人可出現在多個場景，同一場景可有多人 |
| 相處段落（encounter） | 代理和同一情境連續互動的一段，由一到數個 session 組成。段落內情境不變 |
| 對話流（stream） | 一個案例中，所有段落依時間排成的一條序列。這是記憶系統唯一的輸入 |
| 世界線 | 第一章的比喻，等同於「情境」，不在規格中另外使用 |

## 3. 記憶的適用範圍（核心設計）

每一條**植入的事實**都標有適用範圍，只用於出題與計分，不給記憶系統看：

| 範圍 | 意思 | 例子 |
|---|---|---|
| 情境限定 | 只在 `(p, s)` 成立 | A 在工作上要求報告用條列式 |
| 人限定 | 對 `p` 在所有場景成立 | A 對花生過敏 |
| 場景限定 | 對 `s` 的所有人成立 | 這個專案的文件一律用英文 |
| 可遷移 | 不限人與場景 | 「做簡報前先確認聽眾是誰」這類做法 |

**刻意製造的混淆**（參考 SpeakerBind）：不同情境會有**同一屬性、不同值**的事實，例如 A 喜歡條列式、B 喜歡長段落，所以光看話題相關度無法判斷該用哪一條。

## 4. 題目類型

每題在某個段落結束時提出。提問本身不帶身分；作答時附上當下段落的最後幾輪對話，作為「現在是誰、在哪裡」的唯一線索。

| 類型 | 正確作法 | 量的是 |
|---|---|---|
| Q1 本情境 | 用當下情境的記憶 | 基本記憶 |
| Q2 同人跨場景 | 用同一人在別的場景說過、屬於「人限定」的事實 | 認出同一個人 |
| Q3 同場景跨人 | 用別人在同一場景建立、屬於「場景限定」的慣例 | 認出同一個場景 |
| Q4 遷移 | 用別的情境中「可遷移」的經驗 | 遷移 |
| Q5 陷阱 | 別的情境有同屬性不同值的事實，必須用本情境的值 | 誤用 |
| Q6 情境不明 | 段落太短或線索不足，無法判斷是誰；應先確認或給條件式回答 | 不確定時的行為（參考 TANGLE） |
| Q7 無資料 | 本情境從未提過，別的情境有；應說不知道或先確認，而不是套用別人的 | 誤用的另一種形式 |

## 5. 實驗條件

| 條件 | 給記憶系統的訊號 | 角色 |
|---|---|---|
| `label` | 每段都標明是哪個人、哪個場景 | 上界（有人告訴你是誰） |
| `boundary` | 只標明段落邊界，不說是誰 | 中間 |
| `none` | 什麼都不標 | **主要條件** |

**線索強度**（可控變數）：

| 等級 | 對話中能認出是誰的線索 |
|---|---|
| 弱 | 幾乎沒有：不同人講話方式相同、不自我介紹（類似 SpeakerBind） |
| 中 | 角色相關用語、常提的同一批人事物（類似 GroupMemBench） |
| 強 | 固定語氣與口頭禪、常提家人或同事的名字、反覆提到自己的處境 |

報告時要畫出「線索強度 × 條件」的表現，而不是只給一個總分。

## 6. 指標

全部能用確定性方式計分的，就不用 LLM 評審。

| 能力 | 指標 | 計分方式 |
|---|---|---|
| C1 | 段落邊界偵測的 F1 與 AUC（容許 ±1 輪的誤差） | 確定性 |
| C2 | B³ F1、切碎率（同一情境被拆成多個）、污染率（不同情境被合併）；沿用 EvoSpeakerMem 的「首次出現即綁定」因果評估 | 確定性 |
| C3 | 各類題目正確率；**誤用率**（回答中出現別的情境植入的值）；**遺漏率**（該用的本情境事實沒用到）；**遷移率**；取回內容中屬於別人的比例 | 植入的值是唯一字串，以字串比對為主，必要時才用 LLM 評審 |
| C4 | 該確認時有確認的比例；不該確認時亂確認的比例 | 回答格式要求明確標記「確認」，確定性計分 |

## 7. 資料來源（待決定）

| 方案 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A. GroupMemBench 衍生 | 已驗證的重組方式（同作者、同頻道、同一天 = 一段）；只測 C1、C2 | 立即可用，內容有中等強度的身分線索（不給標註時同作者 26%–35%，隨機 6%–17%） | 原本是人對人的群組訊息；只有 715 題，而且不考記憶適用性，**C3、C4 無法用它測** |
| B. 自建 | 先程式產生結構化的世界設定（人、場景、植入的事實與範圍），再由語言模型把事實寫成一對一對話 | 能完整控制範圍、混淆、線索強度；C1–C4 都能測 | 工作量最大；生成品質需要驗證 |
| **建議：A + B** | A 先用來開發與驗證 C1、C2 元件；主實驗用 B | | |

## 8. 自建資料的產生流程（方案 B）

1. **世界設定**（程式產生，可重現）：人數、場景數、每人參與的場景、植入的事實與範圍、混淆配對、時間軸。全部由 `seed` 決定。
2. **對話生成**：每個段落由語言模型依「這段要自然帶出哪些事實、這個人的說話特徵、線索強度」寫成代理與使用者的對話。
3. **自動檢查**：
   - 植入的值確實出現在對話中；
   - 沒有意外洩漏身分，例如直接寫出代號；
   - 弱線索等級中，沒有出現強線索才該有的特徵。
4. **不看記憶也答得出的題目要剔除**（參考 PairPref）：只給題目和當下段落、不給歷史時，若模型就能答對，代表題目太容易，剔除。
5. **人工抽查**：抽樣檢查對話是否自然、植入事實是否正確、題目答案是否唯一。份數待決定。

## 9. 建議規模（待決定）

| 項目 | 建議 | 理由 |
|---|---|---|
| 每案例人數 | 4–8 | 太少沒有挑戰，太多生成成本高 |
| 每案例場景數 | 3–4 | 足以形成複合情境 |
| 每人參與的場景 | 2–3 | 才有 Q2 |
| 每案例段落數 | 80–150 | 對話流長度約數萬到十幾萬 token |
| 時間跨度 | 數週到數月 | 要考跨天、跨週的再辨識 |
| 案例數 × 線索強度 | 每個強度 10–20 個案例 | |
| 題目數 | 每案例 30–60 題，總計約 1,000–2,500 題 | 每類題目至少約 100 題，才能算信賴區間 |

## 10. 對照組

| 對照組 | 目的 |
|---|---|
| 不用記憶 | 下界 |
| 全部歷史放進 context | 只在放得下的規模使用 |
| 一般 RAG（全域檢索） | 現行做法，預期會誤用 |
| RAG + 依標註隔離（`label` 條件） | 上界參考：知道是誰時能做到多好 |
| 依強度或時間排序（FadeMem 衰退、Pragma 式沉寂與喚醒） | 「記憶強度 ≠ 情境適用性」的對照 |
| 無邊界切分（SCALE-QA 的 TSIM） | 只切分主題、不分人 |
| 分群歸屬 + 範圍限定 | 簡單的兩段式基準 |
| 本研究的方法 | — |

## 11. v0.1 的待決定事項（已回覆，見 §12）


1. **場景清單**：要哪些場景？建議 3–4 個差異明顯、但會有同一批人跨足的，例如「工作專案、家庭事務、運動社團、學習課程」。
2. **資料來源**：是否採「A + B」？
3. **對話生成用的模型**：只用本機模型，還是可以用付費 API？生成品質會直接影響基準的可信度。原本的限制是不使用付費 API。
4. **人工抽查的份量**：能抽查多少份？有沒有第二位標註者可以算一致性？
5. **規模**：§9 的建議是否可行？
6. **回答格式**：要開放式回答（較真實，但計分較難），還是選擇題或要求明確標記（計分確定，但較不自然）？建議主實驗用開放式回答，同時要求回答中標記用到了哪條記憶，以便確定性計分。
7. **語言**：英文（方便和現有文獻比較）還是中文（較少人做，但比較基準少）？

### 12.1 四個場景的特性

四個場景的人數、重複出現的頻率差異很大，正好涵蓋不同難度：

| 場景 | 人數 | 同一人重複出現 | 主要難點 | 主要題型 |
|---|---|---|---|---|
| 家庭事務 | 2–6 | 非常頻繁 | 人少、彼此熟悉，常提到彼此（「幫我問我太太」）；容易把家人之間的偏好混用 | Q5 陷阱、Q2 同人跨場景 |
| 公司多人秘書 | 5–20 | 頻繁 | 每人的行程、習慣、權限不同；同一個請求（訂會議室）每人的細節不同 | Q1、Q5、Q3 同場景跨人（公司慣例） |
| 班級課程 | 20–40 | 中等（依課表） | 人多、說話方式相近（同齡學生）；屬於弱線索的天然情境 | Q2、Q5、C2 長期歸屬 |
| 開放場域多功能工作 | 固定同事數人 + 來往的訪客數十人（多為一次性） | 同事頻繁、訪客少 | 代理**像在那裡工作的員工**：要記得同事的習慣與交辦事項，同時認出「這是新的訪客」而不是錯接舊人，並把一般做法遷移到新訪客 | Q4 遷移、Q6 情境不明、Q7 無資料；同事部分另有 Q1、Q5 |

**跨場景的人**（複合情境的關鍵）：同一個人在多個場景出現，例如家長同時是公司員工；學生在家裡是孩子；某位家長到開放場域辦事。每個案例的跨場景人數是可調參數。

**每個案例的結構**：一個代理同時服務若干場景，人數合計 2–60。小案例只有一兩個場景；大案例四個場景都有。

### 12.2 一律使用本機模型的影響

- **對話生成**：Z13（128 GB 統一記憶體）能跑的最大模型，需實測每秒輸出 token 數後才能估算總時間。粗估：每段對話約 6–10 輪、500–800 token；60 人的大案例約 150–250 段，**一個案例約十幾萬 token 的生成量**。若每秒 10 個 token，一個大案例要 4–6 小時。規模要依實測吞吐量調整。
- **品質風險**：本機模型較容易重複、照抄提示的範例（實驗 B 的流程檢查已看到 0.6B 模型照抄提示 28%）、或漏寫植入的事實。§8 的自動檢查要更嚴格，而且要報告剔除率。
- **生成模型與受測模型要分開**：生成對話的模型，不應同時當作答模型，避免模型「認得自己寫的東西」。至少要用不同家族。

### 12.3 2–60 人的規模

- 人數是案例層級的參數，報告時依人數分組（例如 2–6、7–20、21–60），因為人數直接影響歸屬難度。
- 大案例的對話流可能超過本機模型的 context 長度，「全部歷史放進 context」的對照組只能在小案例使用。

### 12.4 雙語與翻譯包

**問題**：計分依賴植入值的字串比對。翻譯時若植入值的譯法不一致，計分會出錯。

**作法**：

1. **原始語言**：待確認（§13 第 3 點）。
2. **植入值以代碼儲存**：每個植入值在世界設定中有代碼（如 `F0123`）與各語言的寫法。翻譯包附上**植入值對照表**，翻譯時照表填寫，而不是自由翻譯。
3. **人名與地名**：每個人有各語言的名字（中文名、英文名），也列在對照表中。
4. **翻譯包內容**：
   - `dialogues.jsonl`：每輪對話一行，含段落代碼、輪次、說話者角色（使用者／代理）、原文、空白的譯文欄；
   - `questions.jsonl`：題目、參考答案與空白譯文欄；
   - `glossary.csv`：植入值代碼、原文、譯文欄；人名、地名、場景慣例用語；
   - `README`：翻譯規則，例如不得增刪事實、口語程度要保留、身分線索（口頭禪、稱呼）要保留，否則會改變線索強度。
5. **翻譯後的檢查程式**：確認每個植入值的譯法都出現在對應段落、對照表沒有遺漏、段落與輪次數一致。翻譯本身不改世界設定與答案。
6. **翻譯量估計**：依 §9 的規模，總量可能達數十萬字。可考慮只翻譯一部分案例當作中文測試集，或改為直接以兩種語言分別生成（同一個世界設定、各自生成對話；不是翻譯，因此兩種語言的對話內容不同，但事實與答案相同）。

## 13. 已確認事項（2026-11-12）

1. **開放場域多功能工作**：在公共空間服務大量來往的人（例如社區中心、圖書館服務台、活動現場），**也有固定的人，例如同事**。代理的角色就像在那裡工作的員工。§12.1 已更新。
2. **人工抽查**：10 個案例、每案例抽 10 道題目與對應段落，共約 100 題。
3. **原始語言與翻譯**：英文為原始語言。中文版由研究者用自己訂閱的閉源模型翻譯，不在本 repo 的生成流程內。因此：
   - 本 repo 的資料生成仍然一律使用本機模型；翻譯是研究者在外部完成的步驟。
   - 中文版要記錄翻譯所用的模型名稱、版本與日期；由於閉源模型會更新，中文版無法完全重現，論文中要說明。
   - 翻譯包要為「交給 LLM 翻譯」而設計：依段落切成適合一次翻譯的大小，每段附上該段會出現的對照表條目，並附一份翻譯指示（植入值、人名照表、保留口頭禪與稱呼等身分線索、不得增刪事實）。
   - 翻譯後由 §12.4 的檢查程式驗證；另外抽查少量段落，確認語氣與身分線索有保留。抽查份量待定，建議與 §13 第 2 點的人工抽查合併進行。
4. **翻譯量**：全部翻譯。
