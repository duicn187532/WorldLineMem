# 混合記憶庫協定（自建，非官方 benchmark）

狀態：第一部分已實作（`memora_mixed`）；第二部分尚未設計。建立日期：2026-11-11。

> 這是本研究自己定義的實驗協定。它的結果一律標示為 `derived_protocol:*`，必須和官方 benchmark 的結果分開報告，不能稱為「Memora 的分數」。

## 1. 為什麼需要它

研究的特色主張是：同一個記憶庫的 agent 會面對不同的人和場景，另一個情境的記憶可能因為相似而被取出、並被當成在這裡也成立（誤用）。公開 benchmark 量不到這件事：

- STALE、LongMemEval、Memora 都是單一使用者。
- GateMem 是多人，但提問者身分是給定的，而且重點是權限。
- SCALE-QA 沒有 session 邊界，但只有單一使用者。

## 2. 設計原則

1. **答案相關的部分全部沿用官方，不做任何修改**：對話內容、題目、評分用的是非子問題、judge prompt、`fama_score`。
2. **只改變「歷史怎麼組成」**：把多個人的對話交錯成一條對話流，寫進同一個記憶庫。STALE 和 SCALE-QA 也是用混入其他對話的方式組成歷史。
3. **退化性**：只有一個人、不給訊號、不附當前對話時，產生的 prompt 和官方 Memora 逐字相同（有測試）。
4. **可重現**：對話流完全由 `seed` 決定。

## 3. 第一部分：量測「誤用」

### 3.1 來源：Memora weekly

- 10 個 persona 的對話都落在同一週（2025-06-01 至 06-07），每人 145–163 個 session、15 題。
- 題目文字高度重疊：65 種題目文字中有 21 種至少兩人共用，5 種是 10 人共用（例如「我這週花了多少錢買咖啡？」）。同一個問題、每個人答案不同。
- 約三分之一的 session 是閒聊，內容看不出是誰。

### 3.2 對話流的組成

- persona 依 `seed` 洗牌後，每 `group_size` 人一組。一組是一個案例，案例之間記憶隔離。
- 組內每個人得到代號 `U1..Uk`。**persona 名稱不會出現在任何記憶方法看得到的地方**，因為名稱就是職業，等於直接說出這段對話是誰的。
- 每一天，組內的人依洗牌後的順序輪流。一個人當天的全部 session 連在一起，稱為一個**區塊**，代表 agent 連續和同一個人相處的一段時間。區塊內維持原本的 session 順序。
- 每個人的題目在「他在提問日的最後一個區塊」結束後立刻提問。排在後面的人的區塊這時還沒進入記憶。

### 3.3 agent 對情境知道多少（`context_signal`）

| 設定 | session 和提問附帶的訊號 | 方法要自己做的事 |
|---|---|---|
| `label` | 說話者的代號（`U3`） | 無，身分是給定的 |
| `boundary` | 所屬區塊的匿名代碼（`b0017`） | 把今天的區塊和前幾天同一個人的區塊連起來 |
| `none` | 沒有任何訊號 | 自己切分區塊，再把區塊連起來 |

三種設定下，作答 prompt 的結尾都會附上提問前的最後 `lead_in_sessions` 個 session（預設 1 個）作為「當前對話」。原因是「我的步數目標是多少」這種問題，不知道是誰在問就沒有答案。

`label` 和 `boundary` 的差距是「跨區塊認出同一個人」的代價；`boundary` 和 `none` 的差距是「自己偵測情境切換」的代價。

### 3.4 作答 prompt

以官方 `PromptBuilder` 的輸出為基礎，做三件事（程式用 assert 確認官方原句存在，官方文字若改動會直接報錯）：

- 把歷史開頭的官方句子換掉。原句：`The following contains all your previous conversations with this user, in chronological order:`。新句說明這些對話來自記憶、agent 會和多個人對話、某段對話可能屬於別人。
- 把 system prompt 中的 `The conversation history below contains ALL your previous conversations with this user` 換成同樣意思的說明。
- 在題目前加上 `# Current Conversation` 段落。有訊號時，每個 session 標題後會加上 `[context: …]`，並在當前對話段落寫出 `Current context: …`。

所有 `group_size` 用同一套 prompt，所以不同人數的結果只差在記憶庫的內容。

### 3.5 指標

- **FAMA×100**：官方 `ModelEvaluator` 加 `fama_score`，和 Memora 相同。
- **干擾量**：同一個方法在 `group_size = 1` 和 `group_size = K` 的 FAMA 差距。
- **誤取率（`foreign_retrieval`）**：交給作答 prompt 的記憶單元中，屬於別人的比例。確定性計算，不需要 LLM judge。另外報告「至少取到一個別人單元的題目比例」。
- **各人的 FAMA（`fama_by_asker`）**：用來檢查提問順序的影響。

### 3.6 對照組

| 對照組 | 設定 | 意義 |
|---|---|---|
| 全部共用 | `rag` 或 `full_context`，`scope = "global"` | 現行做法；預期會誤用 |
| 依訊號完全隔離 | `scope = "context"` | 只看訊號相同的 session。搭配 `label` 時是「不會誤用」的參考上限，但沒有任何跨人遷移；搭配 `boundary` 時等於只記得當前這一段 |
| 單人參考 | `group_size = 1` | 沒有其他人時的分數 |
| 之後的方法 | 讀取時檢查適用性 | 目標是在 `none` 或 `boundary` 下接近 `label` 加隔離的分數 |

`scope = "context"` 在 `none` 設定下會直接報錯，因為沒有訊號可以隔離。

### 3.7 已量到的結果（不需要模型）

BM25、以一問一答為單位、取前 20 個，全部 150 題，3 個 seed：

| 人數 | 屬於別人的單元比例 | 隨機取的期望值 | 完全沒取到本人單元的題目 |
|---|---|---|---|
| 1 | 0% | 0% | 0% |
| 2 | 44.1%–44.6% | 50% | 0% |
| 5 | 71.5%–72.0% | 80% | 0%–1.3% |
| 10 | 81.8% | 90% | 7.3%–8.0% |

每一題都至少取到一個別人的單元。一般檢索在「這是誰的記憶」上只比隨機好一點。這是檢索層的數字，還不是作答正確率。

### 3.8 規模與本機可行性

| 人數 | 案例數 | 每案例 session 數 | 每案例對話流長度（cl100k 估算） |
|---|---|---|---|
| 1 | 10 | 145–163 | 約 4.9 萬–5.8 萬 token |
| 2 | 5 | 約 300 | 約 10 萬–11 萬 token |
| 5 | 2 | 約 780 | 約 26 萬–27 萬 token |
| 10 | 1 | 1,551 | 約 53 萬 token |

每種設定都是 150 題。完整歷史對照組只在 1 人和 2 人時放得進本機模型；5 人以上只能跑記憶方法。

### 3.9 限制

- **情境只差在「人」**：沒有場景或任務的差別。
- **資料是合成的**：Memora 的對話由 LLM 產生；每個人的對話是獨立生成的，彼此沒有關聯（例如不會提到對方）。
- **`none` 可能落在地板**：閒聊 session 本身看不出是誰，能不能歸屬完全靠對話流中的位置。如果所有方法在 `none` 下都一樣差，這個條件就沒有鑑別力，屆時要以 `boundary` 為主要條件。
- **提問位置不同**：排在前面的人提問時，記憶庫裡的別人內容比較少。要用多個 seed 平均，並報告 `fama_by_asker`。
- **prompt 不是官方的**：三句話被替換、多了一個段落。所以即使 `group_size = 1`，只要用 `prompt = "mixed"`，分數也不能和官方 Memora 的數字並列。
- **繼承 Memora 的問題**：單一本機 judge、官方 Track 1 沒有當日日期（見 BENCHMARK_MATRIX.md）。

## 4. 第二部分：量測「遷移」（尚未設計）

要量「A 情境的經驗在 B 情境有沒有被用上」，必須新寫題目，現有資料重組不出來。已決定的原則：

- 等第一部分的對照組結果出來、知道現有方法錯在哪裡之後再設計。
- 規模控制在 100–200 題，定位是診斷用的小型測試集，不當成論文的 benchmark 貢獻。
- 每一題由研究者人工確認，並記錄建構流程。
- 題目型態：做法可以共用、偏好的具體值不能共用的成對情境（參考 ShareMem 的切法）。

## 5. 使用方式

```powershell
# 兩人共用、沒有訊號、一般 RAG（工程驗證用的小模型）
wlmem run configs\smoke\mixed_k2_none_rag_global.toml
wlmem evaluate configs\smoke\mixed_k2_none_rag_global.toml
```

`[benchmark]` 的參數：

| 參數 | 預設 | 說明 |
|---|---|---|
| `period` | `"weekly"` | Memora 的時間長度 |
| `personas` | 全部 10 個 | 要納入的 persona |
| `group_size` | persona 總數 | 每組人數；必須整除 persona 數 |
| `context_signal` | `"none"` | `"label"`、`"boundary"`、`"none"` |
| `lead_in_sessions` | 1 | 附在 prompt 結尾的當前對話 session 數 |
| `seed` | 0 | 決定分組、代號和每天的輪流順序 |
| `question_limit` | 無 | 每個人只問前 N 題（工程驗證用） |
| `prompt` | `"mixed"` | `"official"` 只在 1 人、無訊號、不附當前對話時可用，用來驗證退化性 |

## 6. 報告規則

- 結果表格的標題必須寫明「自建協定」。
- 必須同時報告 `group_size`、`context_signal`、`seed`、`lead_in_sessions`。
- 比較不同方法時，以上四項加上作答模型和 judge 必須完全相同。
- 正式結果至少用 3 個 seed。

## 7. 可行性檢查：沒有任何訊號時，能不能分出是誰（2026-11-11）

`python scripts/diagnose_attribution.py`（`--user-only` 只用使用者發言；`--embed-model` 加嵌入模型）。`context_signal = "none"`，人數 2／5／10，seed 0–2；gold 的 session 歸屬只用來計分；以 TF-IDF 表示每個 session，全部是因果的（只和之前的 session 比）。

| 人數 | 新相處段落開始的偵測 AUC（0.5 = 隨機） | 最相近的先前 session 是同一人 | 新段落開始時認出是哪位舊識：逐 session | 同左：整段合併（假設已知段落邊界） | 隨機 |
|---|---|---|---|---|---|
| 2 | 0.50（只用使用者發言 0.51） | 55%（56%） | 43%（44%） | 58%（59%） | 50% |
| 5 | 0.47（0.50） | 26%（28%） | 23%（16%） | 29%（28%） | 20% |
| 10 | 0.46（0.50） | 16%（19%） | 17%（12%） | 18%（18%） | 10% |

**解讀**：在 Memora 上，光看文字內容幾乎分不出是誰。連「同一段相處中前後兩個 session」都不會比較像。抽樣檢查原因：Memora 的使用者發言多是一般性的話題（「流行文化有哪些趨勢」），不同 persona 的說話方式和內容幾乎一樣，人物特徵只出現在少數 session。

**結論**：Memora 不適合當 `none` 條件的資料來源。在它上面，任何方法在 `none` 下都會落在地板，量不出方法之間的差異（§3.9 預告的風險成真）。`none` 條件需要「原則上能從內容認出是誰、但不容易」的資料，例如每位使用者有固定語氣、角色與生活事件的對話。嵌入模型版本的結果待補。
